# QuestionForge 压测报告与方法

> 记录日期：2026-09-20　｜　脚本：`seed.js`（造数据）+ `loadtest.js`（压测出报告，均零依赖）
> 说明：全程在**隔离测试库**（`questionforge_test`）上跑，`QF_MOCK=1`，不动生产数据、不产生 API 费用。

## 一、环境与方法（为什么这样设计）

| 项 | 说明 |
|---|---|
| 机器 | 12 核，Node v24.14.1 |
| 拓扑 | **客户端与 MySQL 同机**（会互相抢 CPU，所以数字偏保守，报告里必须写明这一点，否则读者无法判断含义） |
| 数据集 | `questions` 1 万（本次）、可扩到 5 万 / 20 万；`qstate` 一半有学习状态；4 种题型 × 12 章 × 40 考点 × 难度 1–3 |
| 并发档位 | 10 / 30 / 100；每场景每档 400 个请求 |
| 压什么 | 只压 **DB/API 层**：题库列表（带筛选）、筛选项、统计、答题写入 |
| **不压什么** | **真实模型调用**（会烧钱）。要压流水线并发必须用 `QF_MOCK=1`，测的是调度与写库能力，不是模型速度——这一点必须在报告里写清，否则等于把 mock 吞吐当真实产能 |

三条纪律：同一台机器、同一数据集快照、同一并发档位。跑对比用 `node loadtest.js --diff before.json after.json`。

## 二、结果（1 万题数据集）

| 场景 | 并发 | QPS | p50 | p95 | p99 | 错误率 | 每次请求 SQL 数 |
|---|---|---|---|---|---|---|---|
| read（列表/筛选/统计） | 10 | 35.4 | 224 | 448 | 469 | 0% | 6.6 |
| read | 30 | 35.6 | 636 | 1720 | 1757 | 0% | 6.6 |
| read | 100 | 35.6 | 2062 | 6057 | 6262 | 0% | 6.63 |
| write（答题写入） | 10 | 205.5 | 42 | 77 | 162 | 0% | 5 |
| write | 30 | 263.7 | 106 | 149 | 158 | 0% | 5 |
| write | 100 | 209.1 | 464 | 514 | 542 | 0% | 5 |
| mixed（读 4:写 1） | 10 | 42.2 | 198 | 443 | 470 | 0% | 6.29 |
| mixed | 30 | 43.5 | 544 | 1457 | 1496 | 0% | 6.28 |
| mixed | 100 | 43.5 | 1779 | 4910 | 5193 | 0% | 6.28 |

**读一遍这张表能看出什么**（这才是压测的价值）：

1. **写路径正常**：QPS 205 → 264 → 209，延迟随并发温和上升，说明写入（upsert + 流水插入）没有明显争用。
2. **读路径有硬瓶颈**：并发从 10 加到 100（10 倍），**QPS 死死卡在 35.6 不动**，而 p95 从 448ms 涨到 6057ms（13 倍）。
   吞吐不涨、延迟线性恶化 = **请求被串行化了**，不是"机器不够"。

## 三、瓶颈根因（用 EXPLAIN 定位，而不是猜）

对 `practiceList` 的真实查询做 EXPLAIN：

```
q | type=ALL   | key=无      | rows=8368 | Using where; Using temporary; Using filesort
s | type=eq_ref| key=PRIMARY | rows=1    | Using where
```

**根因**：排序表达式 `ORDER BY CASE WHEN s.last_right=0 THEN 0 ... , s.last_ts DESC` **无法走索引**，
MySQL 必须把**全部 1 万条候选行（join qstate 之后）拉出来做 filesort，再取前 30 条**。
所以每个请求的开销都和"你题库里有多少题"成正比，而不是和"你要看多少题"成正比。

**顺手验证了"加索引是否能解决"**（这一步很关键，避免得出错误结论）：

| 方案 | 耗时 | EXPLAIN 变化 |
|---|---|---|
| 原始查询 | 46 ms | type=ALL，rows=8368，filesort |
| 加 `(user_id, status, created_at)` 复合索引 | **38 ms** | type=range，rows=4185，**仍然 filesort** |

**结论：索引只让耗时从 46ms 降到 38ms（-17%），因为 filesort 的规模没变。**
这说明"性能问题就加索引"是错的判断——真正的矛盾是**每请求排序 1 万行**这件事本身。

## 四、优化方向（按性价比排序，都还没实施）

1. **把排序键物化，让排序能走索引**（收益最大）：在 `qstate` 上加一个 `prio TINYINT`（错题=0 / 未做=1 / 半会=2 / 已会=3），
   答题时顺带更新它，并建 `(user_id, prio, last_ts)` 复合索引。这样排序可以走索引、**彻底消除 filesort**，
   耗时只与"取多少条"相关，不再与"题库多大"相关。
2. **两段式查询**：先用覆盖索引取出符合条件的 id（只走索引不回表），再按 id 批量取详情。适合筛选条件多、返回列少的场景。
3. **缩小候选集**：强制或默认带上"批次/章节"筛选（用户实际使用时基本都会筛），把 filesort 规模从 1 万降到几十。
   （这个改动最小，但属于"把问题绕开"，适合当过渡方案。）

## 五、怎么自己跑更大数据集

```bash
# 1) 起测试服务（必须 QF_MOCK=1，否则会真花钱调模型）
QF_MOCK=1 QF_DB_NAME=questionforge_test QF_RATELIMIT=off QF_PORT=8541 QF_DATA_DIR=data/test-env node server.js

# 2) 造 5 万题（约 3~5 秒）
QF_DB_NAME=questionforge_test node seed.js --questions=50000 --users=1000 --tasks=1000 --attemptsFrom=20000

# 3) 压测（耗时随数据量线性增长，5 万题下单档约 1~2 分钟）
QF_DB_NAME=questionforge_test QF_BASE=http://localhost:8541 node loadtest.js --concurrency=10,30,100 --label 5w

# 4) 优化的前后对比（用 git 切到优化前的提交跑基线）
node loadtest.js --diff data/loadtest/loadtest-before-*.json data/loadtest/loadtest-after-*.json
```

报告会自动落到 `data/loadtest/loadtest-<label>-<时间>.json` 与同名 `.md`。

> 两个安全提醒（脚本都内置了保护）：
> ① `seed.js` 与 `loadtest.js` 都会**校验目标库名必须含 test**，否则直接退出——这个项目真实发生过"临时脚本误写生产库"，
> 所以造数据脚本的第一道防线是硬校验，而不是靠人记得设环境变量；
> ② 压测接口会改动数据（答题/收藏），**永远只在测试库上压**。

# 附：优化实施（同日完成，含实测数字）

## 做了什么

按上文第四节的方案①实施了改造，并顺带把不变式补齐：

1. **物化排序优先级**：`qstate` 增 `prio`（0 错题 / 1 未做 / 2 半会 / 3 已会），答题时由 `recordAttempt` 同步维护（答对→3，答错→0）。
2. **索引与 ORDER BY 逐字段对应**：建 `(user_id, prio, last_ts DESC, question_id)`。
3. **建立不变式「qstate 行 ⟺ 该题可练习」**（这是关键，也是最后才想通的一步）：
   迁移清理历史 → 题目入库时补行 → 驳回/打回时删行 → 查询前双向自愈。
   有了它，列表/计数/汇总都**不再需要跨表的 `q.status` 过滤和 join**。

## 卡住的三个点（比结果本身更值得记）

| 现象 | 我的判断 | 实际原因 |
|---|---|---|
| 加了普通索引只快 17%（46→38ms） | 以为索引选错了 | ORDER BY 里含**另一张表**的字段（`q.created_at`），MySQL 必须 filesort，索引再好也没用 |
| 换了「方向匹配」的降序索引，仍然 filesort | 以为方向不对 | 同上：只要有一个排序键不在索引里，就必然排序 |
| 拆掉跨表 status 过滤后，列表快了但接口整体还是 140ms | 以为索引还没生效 | 同接口里还有**两条**我漏改的查询（`total` 计数与 `counts` 汇总）仍带着 5 万行 join |

结论：**性能优化最难的不是改哪里，而是确认"到底哪一句在拖后腿"。** 必须一条条单独计时（而不是只测整个接口），否则会把"另一个查询的开销"记到已经优化好的查询头上。

## 实测结果（5 万题数据集，预热后 30~50 次平均）

| 指标 | 改造前 | 改造后 | 提升 |
|---|---|---|---|
| 列表查询 | 125 ms（filesort） | **0.8 ms**（走 idx_qstate_sort，无 filesort） | **~150×** |
| 汇总统计 | 230 ms | 36.5 ms | 6.3× |
| **接口整体**（列表+条数+汇总） | ~355 ms | **53 ms** | **~6.7×** |

排序语义未变：首行仍是 prio=0（错题优先）；错题本、章节/题型筛选、分页都验证通过。

## 优化后暴露的下一个瓶颈（诚实记录，未修）

在同一份 5 万题数据上再压一次，**写路径反而更慢了**：write 场景 QPS 从 1 万档的 264 掉到 25。

根因不是这次改动，而是 `/api/practice/answer` 里调用了 `getMyState(userId)`——它每次把**该用户的全部 qstate 行（5 万行）拉进内存**只为了取一道题的状态。这是与"列表全量加载"同类的残留问题。

**这恰好是性能优化最真实的规律：消灭一个瓶颈之后，下一个瓶颈才会浮出来。** 下一步应把它改成按题查询（`WHERE user_id=? AND question_id=?`）或用小缓存。

# 附二：第二轮优化（把同类问题一次清干净）

第一轮只解决了"列表查询"这一处。做法是靠压测反复验证，把**同一根因的其它位置**也找出来逐个消除。

## 三类同根因的问题

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `/api/practice/answer` | `getMyState` 每次把该用户**全部** qstate 行（5 万行）拉进内存，只为取一道题的状态 | 新增单行查询 `getQuestionState(userId, qid)`；stats 路由里 3 个计数也改为纯 qstate 查询（去掉 join） |
| 2 | `/api/practice/filters`、`/api/practice/stats` | 4 组 / 3 组 `GROUP BY ... JOIN`，5 万题下分别 282ms / 557ms | 各加 30 秒 TTL 缓存（下拉选项与正确率统计不是实时关键路径）；并删掉 stats 里一次**调了却没用**的 `practiceFilters` |
| 3 | `listAttempts` | `ORDER BY id DESC` 与索引 `(user_id, ts)` 不匹配 → filesort | 改为 `ORDER BY ts DESC`，走索引 |

## 实测（5 万题、并发 30、客户端与 MySQL 同机）

| 场景 | 本轮开始前 | 优化后 | 提升 |
|---|---|---|---|
| **write**（答题） | 25 QPS / p95 4303ms | **527.7 QPS / p95 69.7ms** | **~21×** |
| **read**（列表/筛选/统计） | 10.7 QPS / p95 6605ms | **52.2 QPS / p95 923ms** | **~4.9×** |
| **mixed**（读 4:写 1） | 13.3 QPS / p95 5565ms | **66 QPS / p95 764ms** | ~5× |
| 每次请求 SQL 数 | 6.73 | **3.81** | −43% |

单端点（串行平均）：列表 52ms、筛选项 3ms（缓存）、统计 163ms（首跑后走缓存）。

## 明确记录、不再继续追的两处（这是判断力，不是遗漏）

1. `/api/practice/stats` 里的 `weakKPs` 聚合约 160ms（按考点统计薄弱项，要 JOIN + GROUP BY）。
2. **带 questions 侧筛选（章节/题型/难度/批次）的列表查询仍需 join**，排序会退化为 filesort（213ms）——
   因为筛选维度在 `questions` 表上，而"边扫索引边取、命中 LIMIT 即停"要求所有条件都能落在 qstate。
   彻底解决要把这些筛选维度**冗余进 qstate**（多 4 列 + 索引），属于下一步的架构调整；
   当前 213ms 只发生在用户主动筛选时，可接受。

**为什么停在这里**：这两个都只在低频路径（统计页、主动筛选）上，投入产出比已经很低；
把边界和原因写清楚，比继续加索引更有价值——**知道"哪里不值得继续做"和知道"怎么做"同等重要**。

## 顺带修掉的一个测试缺陷（值得单独说）

全量套件里 `feature_test` 偶发失败一条（单跑却通过）。根因是**测试自己污染了共享状态**：
「人工裁决落库守卫」那一段用裸 SQL 把某道题改成 `rejected` 后没有还原，
而后续 CSRF 断言里复用的一道题**有时恰好就是它**（题目 id 由时间戳生成，谁排在前面每次不同），
于是表现为"时好时坏"。修法是在该段收尾把题目状态还原，并补一条断言验证已还原。

> 教训：**测试用裸 SQL 改共享数据，必须自己收尾清理**；"偶发失败"几乎总是测试的清理问题，而不是被测代码的问题。
