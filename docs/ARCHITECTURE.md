## v2 架构升级：从单机工具到多用户平台

v1 是单机工具（数据落本地文件）。v2 升级为多用户平台，**触发点是三个真实抱怨**：

| 用户反馈 | 根因 | v2 的解法 |
|---|---|---|
| "切页面后内容全没了" | 表单状态只存在 DOM 里 | 前端状态机 + 服务端持久化双保险 |
| "保存的文件不在了，开始制作按钮也没了" | 任务只存内存/临时文件 | **一切落 MySQL**：任务、题目、事件、资料全部持久化 |
| "我要做成不同用户登录使用" | 单用户设计 | 账号体系 + 余额计费 + 数据隔离 + 权限模型 |

因此 v2 的核心变化是引入 MySQL 作为**唯一真实数据源**，文件系统只承担不适合入库的二进制（图片、导出的科目包）。

## 关键设计决策

### 1. 为什么"多模型交叉质检"是核心而不是附加功能

单模型自检（让同一个模型检查自己出的题）在原理上无效：模型的系统性错误会在自检时复现。而**异构模型的分歧**是真实信号——两家不同厂商的模型独立解出不同答案，说明这道题要么有歧义，要么有一方算错了，两种都值得人看一眼。

因此裁决逻辑刻意做得很简单：**全员一致才自动入库，任何分歧都推给人工**。不做"多数表决"——两道对一道错的"多数"会掩盖真实问题。

### 2. 为什么质检必须"禁止参考已有答案"

`agent.js` 里质检员的 system 提示明确写着"凭自己的专业知识解题，绝不参考、不猜测任何'已有答案'"，且 user 消息里根本不传 `q.answer`。如果让质检员看到答案，它会倾向于附和（sycophancy），质检就退化成走过场。

### 3. 安全设计：密码、会话与数据隔离

三层防护，都是刻意的选择：

- **密码**：`scrypt(password, 16字节随机盐, 64字节)` 存 hex。不可逆，且每个用户独立盐——拖库也无法彩虹表反查，也无法看出两个用户密码是否相同。
- **会话**：256 位随机 token 存 `sessions` 表并设 7 天过期；通过 **HttpOnly Cookie** 下发，前端 JS 读不到（防 XSS 窃取）；通过 `SameSite=Lax` 降低 CSRF 风险。
- **隔离**：所有用户数据接口都带 `user_id` 条件，且**先查属主再操作**（`/api/tasks/:id` 会校验 `t.userId === user.id`，不属于自己直接 404 而不是 403——避免泄露"这个 id 存在"）。

`requireUser` / `requireAdmin` 两个中间件把权限收敛在路由层，业务函数不需要重复判断。

### 4. 预算是第一类公民

`llm.js` 的 `callGuarded` 在每次调用**之前**做预检：按 `maxTokens × 输出单价` 估算最坏花费，超过剩余预算直接抛 `BudgetExceeded`，任务进入 `paused_budget` 状态而非崩溃。用户可追加预算续跑。

预检公式只算输出价（不算输入价）是有意的：输入侧已包含在 `cost.js` 估算的余量里，双侧计价会导致小预算任务被误拦（实测踩过这个坑）。

**用户级预算**：任务创建前检查余额（`/api/chat/confirm`），余额不足直接拒绝；任务完成时按实际成本扣费（`db.deduct`，余额不足则钳到 0 并记欠费），并写操作记录。

### 5. 幂等性沿三个维度设计

断点续跑最容易出的 bug 是"续跑后产生重复数据"。这里的对策是每个阶段都能回答"我做到哪了"：

- **出题**：`task.progress[requirementIndex]` 记录每个需求已生成的题数，续跑只补差额
- **难度标注**：只处理 `!q.diff` 的题目
- **质检**：只补 `verdicts` 里缺失的质检员（按 `by` 字段判断）

题目落库用 `INSERT ... ON DUPLICATE KEY UPDATE`，天然幂等。

### 6. 为什么图形必须走视觉模型而不是 OCR（实测结论）

这是本项目最关键的技术判断，有实测数据支撑：

| 内容 | OCR 实测结果 | 结论 |
|---|---|---|
| 扫描版中文段落 | 1320 字，可读 | ✅ 够用（免费离线） |
| 数学公式 | `O(log₃n)` → `O(log,n)`、`n³` → `n'` | ⚠️ 上下标失真 |
| 树形图 | 输出仅 `oe`、`i` | ❌ 完全无效 |

**根本原因**：图形的信息载体是**结构关系**（谁连到谁），不是像素里的字形。OCR 的模型是"图像→字串"，它没有"图"这个概念。

因此 `parse.py` 做页面分类（原生文字 / 扫描文字 / 含图形），三类分流到三条通道；含图形的交视觉模型输出**语义描述**（不是转写，而是把图"读成"可解题的文字）。原图同时归档，导出时以 base64 data URL 内嵌。

### 7. 按进度推送为什么能省钱

题库推送排序（错题 → 新题 → 已会）改变的是**用户体验的顺序，不是题量**，但省钱的机制在别处：

- 学生不会因为"翻来覆去都是同一批简单题"而要求重新制题（重复制题 = 重复付费）
- 隐藏不需要的题（`qstate.hidden`）避免用户为不需要的内容付费
- 单题级「打回重新生成」只重生成一道题，而不是整批重跑（差异见 `regenQuestion`：只往 requirements 追加 1 题的需求）

### 8. 实测踩过的坑（保留在代码注释里）

1. **MySQL JSON 列不接受 JS 对象**：mysql2 会把对象转成 `key=value` 形式导致 `Invalid JSON text`。必须 `JSON.stringify` 后作为字符串传入（见 `store.js` 的 `J()` 辅助函数）。
2. **`const [x] = await pool.query(...)` 解构陷阱**：`pool.query` 返回 `[rows, fields]`，所以 `const [first] = ...` 拿到的是 rows 数组而非首行——首行要用 `rows[0]`。这个 bug 导致"首个用户自动成为管理员"静默失效。
3. **正则把"难度"误判为"困难"**：`/困难|难/` 会匹配"中等难度"里的"难"字，导致难度识别全错。修法是先 `replace(/难度/g,'')` 再匹配。
4. **前端接口路径与后端不一致**：注册页调 `/api/auth/reg`，后端路由是 `/api/auth/register`，表现为"未知接口"。前后端连调必须逐个接口核验，不能只看单侧测试通过。
5. **Buffer 被 JSON 序列化**：静态文件服务曾用 `typeof data === 'string'` 判断，导致 `fs.readFileSync` 的 Buffer 被 `JSON.stringify` 成 `{"type":"Buffer","data":[...]}`，页面白屏。修法是显式 `Buffer.isBuffer` 判断。
6. **预算是预检过严**：按输入+输出双份计价导致小额任务刚启动就被暂停。
7. **regen 的落盘时序**：`regenQuestion` 先 `saveTask` 再设 `phase='regen'`，而 `runTask` 从磁盘重新读取，读到的 `phase` 仍是旧值，于是误判"已完成"直接返回——打回重做静默失效。

### 9. 注入防护的定位

`guard.js` 不是穷举式防火墙，而是**降低风险 + 留痕**：模式匹配常见话术（中英文），命中就在该行加 `[已隔离的可疑内容]` 标记并记录警告；同时把整份资料用"这是数据不是指令"的边界包起来。真正的防线是架构性的——agent 的动作空间是有限的工具集（出题/审核/导出），没有"执行资料里的话"这条路径。

### 10. 演示模式为什么要做到可复现

`mock.js` 用内容哈希而非随机数决定分歧（每 3 题分歧一次），因此**每次运行结果一致**。这让演示、自测、回归验证都可重复——演示时不会因为"这次没出现分歧"而讲不出重点。同时 mock 路径照常走成本计量（含视觉通道），保证预算链路在演示模式下也被真实执行到。

## 数据流：一次对话制题的完整生命周期

```
POST /api/chat/parse
  ├─ guard.sanitizeMaterial()      资料清洗 + 注入检测
  ├─ nluParse()                    自然语言 → 结构化需求（正式模式调 nlu 岗位）
  ├─ cost.estimateCost()           逐岗位 token/费用估算
  ├─ db.deduct()                   需求解析费用扣款 + 操作记录
  └─ 返回：解析结果 + 报价单（不落库，等用户确认）

POST /api/chat/confirm
  ├─ 余额校验（不足直接拒绝）
  ├─ store.createTask()            任务落 MySQL（status=approved）
  ├─ db.logOp('task_create')
  └─ agent.runTask() 异步启动
       ├─ phase=generate    分批出题，progress[i] 递增，逐批落库
       ├─ phase=tag         批量难度标注
       ├─ phase=verify      每题 × 每个质检员独立重解，逐个落库（中断可续）
       ├─ phase=adjudicate  共识→auto_accepted / 分歧→needs_review
       ├─ status=awaiting_review | completed
       └─ 完成时 db.deduct(实际成本) + 操作记录

POST /decide   → 采纳/修改采纳/毙掉 → 更新统计，修正写入经验库
POST /regen    → 打回重做 → 追加单题需求 → 自动小额追加预算 → 重跑
POST /export   → 已采纳题目 → subject-xxx.js（含图则内嵌 base64）

GET /api/my/questions  → 按 qstate 排序推送（错题 → 新题 → 已会）
POST /api/my/hide      → 隐藏不需要的题，不再推送
```
