# 质检环节的验算工具：设计、实验与结论

> 记录日期：2026-10-09　｜　相关代码：`lib/tools.js`（工具）· `lib/solve.js`（有界工具循环）· `lib/agent.js`（接入质检）· `lib/evals.js`（评估与对照实验）
> 复跑实验：`node r6_compare.js`（结果落 `data/tools_compare.json`）

## 一、要回答的问题

题目的答案里有一部分是**算出来的**（数值、百分比、单位换算、多位数运算）。
模型"心算"并不可靠——这一点在另一个独立实验里被量化过：难题集上它的**代码 100% 正确，但它口述的答案稳定错 16.7%**。

于是问题不是"要不要加计算工具"，而是三个更具体的问题：

1. **工具到底能带来多少提升？**
2. **这个提升里，有多少是"工具真的算了"，有多少只是"提示词逼它认真算了"？**（后者便宜得多）
3. 代价是多少？值不值？

## 二、设计与实现

### 工具本身（`lib/tools.js`）

一个纯本地的表达式求值器（`calc`），三条硬约束：

- **纯函数、无 IO、无副作用** → 不需要沙箱，也不会被滥用放大成 RCE
- **确定性**：同输入必得同输出，测试与 mock 可复现
- **自己写词法分析 + 递归下降求值，绝不使用 `eval` / `new Function`**
  （该工具将来会通过对外 API / MCP 暴露给外部调用方，用 eval 等于把远程代码执行送出去）

支持 `+ - * / % ^`、括号、一元负号；函数 `sqrt/abs/floor/ceil/round/ln/log/exp/sin/cos/tan/max/min/pow`；常量 `pi/e`。
自我保护：表达式长度上限 200 字符、求值步数上限 200 步、结果必须为有限数。

安全回归测试（`tools_test.js`，70 项断言）里最重要的一组：
`process.exit(1)`、`require("fs")`、`constructor.constructor("return 1")()`、`__proto__`、`eval(...)`、`Function(...)`
等一律**只能返回错误、绝不执行**；其中最容易把测试进程打挂的几条放在**子进程**里跑，
以便明确断言"子进程正常退出且返回了错误结果"。

### 有界工具循环（`lib/solve.js`）

- **最多 3 轮**（硬上限，传更大的值也只跑 3 轮）；循环发生在**单题内、不跨题**，
  因此**不影响流水线现有的断点续跑语义**（断点仍按"已出题数 / 已质检员数"确定性换算）
- 每轮都是一次正常的 LLM 调用 → 现有计量器自动计费，不需要额外记账
- **工具报错也要喂回模型**（作为 `{error}` 回传），否则它不知道失败了，会继续按自己的假设编
- 用满轮数仍在调工具 → 去掉 `tools` 再问一次强制收口（不依赖 `tool_choice:'none'`，兼容性更好）
- **单轮工具调用上限 5**：超出部分不执行，但**必须补一条 tool 结果消息**，
  否则 `assistant.tool_calls` 与 tool 消息数量对不上、下一次请求会被供应商判格式错误
- **供应商不支持 tools 时降级**：错误为 400/422 且消息提到 `tool`/`function` 时，
  **从干净上下文重跑一次无工具版本**，而不是让整个质检任务失败。
  判定口径故意收紧（宁可漏判、任务失败看得见，也不误判、把 `max_tokens` 这类真问题掩盖成"模型不支持工具"）

### 注入策略（`lib/agent.js`）

- **只在质检环节注入工具**（不在出题环节）：出题靠的是资料取材，不是计算
- **只对"看起来需要计算"的题注入**（`needsCalc`），纯概念题给工具只会产生白调（多花一次调用、零收益）
- `QF_TOOLS=1` 开关控制，**默认关**，可随时回滚
- 结果落进既有的 `verdicts_json`（**不加表、不加迁移**）：
  `tools / rounds / forced / toolFailed / missedCalc / calcMismatch / degraded`
  - `missedCalc`：判据说需要计算、但它一次都没调 → **漏调率的数据来源**
  - `calcMismatch`：模型给出的数字与工具算出的对不上 → **只作为信号存档，不直接进裁决**
    （误报风险：模型可能先用工具算中间值、再自己合并成最终答案，那不是错）

## 三、对照实验：三组，而不是两组

**这是本次最重要的一处设计。** 如果只比"有工具 / 无工具"，就无法区分提升来自工具还是提示词。
所以设三组：

| 组 | 说明 |
|---|---|
| `off` | 无工具、无提示（改动前的行为，基线） |
| `prompt` | **有提示无工具**——要求它一步步算出精确结果再作答，但不给工具 |
| `tools` | 有工具 + 规定必须调用 |

题集：`testdata/golden_calc.js`（10 道**必须算一遍**的合成题，答案均用代码核算；概念题不会触发工具，测不出差异）。

## 四、结果

| 组 | 共识准确率 | 未答率 | 工具调用 | 漏调 | 成本 | LLM 调用 | 墙钟 |
|---|---|---|---|---|---|---|---|
| `off` | 60% | 20% | 0 | 0 | ¥0.0269 | 20 | 21.4s |
| `prompt` | 70% | 15% | 0 | 0 | ¥0.0307 | 20 | 23.3s |
| **`tools`** | **80%** | **10%** | 14 | 9 | ¥0.0707 | 34 | 32.3s |

## 五、结论

1. **提示词贡献 +10pp（60→70），工具再贡献 +10pp（70→80）——两者各占一半。**
   少了 `prompt` 组，很容易把 +20pp 全部归功于工具，那是错的。
   **对产品而言：提示词应当先行**（便宜且拿到一半收益），工具是它的增量。
2. **未答率同步下降**（20%→15%→10%）："算不出来就弃答"的情况变少了。
3. **代价可量化**：成本约 **2.6 倍**、耗时约 1.5 倍。收益不免费，因此工具只对判据命中的题开启。
4. **当前最大的可改进项是漏调**：20 次机会里约 9 次"判据说该算、模型仍然心算"。
   方向：加强提示词，或对纯数值题改用 `tool_choice: 'required'`。

## 六、边界与未决项（诚实记录）

- **判据 `needsCalc` 是启发式的**。在一次自建标注集（10 正例 + 12 负例）上为 100%/100%，
  但那个集子规模小且是照着它调的，有过拟合风险。用一份**独立**的真题库（40 道）验证时，
  它只把 2.5% 判为需要计算——**被漏掉的是"栈的不可能输出序列"这类推理题，而计算器对它们本来就没用**。
  也就是说：判据的"窄"是合理的，真正的缺口在**工具能力本身**，不在判据。
- **推理/模拟类题目本工具无解**（需要代码执行或模拟器），属独立后续项。
- 一处**未能复现的偶发失败**：`QF_TOOLS=1` 全量测试曾出现 1 项失败、重跑即绿，疑与演示模式的
  分题号分布有关，尚未定位。
- 本工具的价值边界：它只覆盖**算术**。它不提升"题目表述是否清晰""考点是否覆盖"这类质量维度。

## 七、怎么复跑

```bash
node tools_test.js           # 工具层：求值正确性 + 安全回归（含子进程断言）
node solve_test.js           # 有界循环：四条路径 + 降级 + 单轮上限
node r4_calibrate.js         # 判据标定：自建标注集上的混淆矩阵
node r6_compare.js           # 三组对照实验（会调用真实 API，约 ¥0.13）
node runtests.js             # 全量 11 个套件（默认关）
QF_TOOLS=1 node runtests.js  # 全量（工具开启）
```
